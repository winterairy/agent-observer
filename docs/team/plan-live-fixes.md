## 0. 배경과 목표

1단계 병합 뒤 실제 Windows 로컬 Claude Code 세션을 연결해 보니, 이벤트 수신은 되지만 화면이 실제 상황과 맞지 않았다. 관찰 서버의 목적은 "지금 무슨 일이 일어나는지 한눈에 믿고 보는 것"이므로 다음을 목표로 한다.

1. 화면에 있는 BOT은 모두 실제로 일하는(또는 방금 끝난) BOT이다. (LIVE-04)
2. 세션·BOT이 쓰는 모델이 보인다. (LIVE-03)
3. 플랜 사용량이 서버 사정 때문에 조용히 비지 않고, `/usage`와 차이가 나는 이유를 안다. (LIVE-01·02)
4. 사무실 화면 하나로 상태·승인 대기·현재 도구·스킬·모델·플랜 사용량을 파악한다. (LIVE-05)

## 3. Task LIVE-04 (High). 내부 에이전트 BOT 제거와 끝난 BOT 정리

### 요구사항

- 내부 에이전트: `SubagentStart`나 도구 이벤트(`PreToolUse`·`PostToolUse`) 없이 `SubagentStop`만 온 `agent_id`는 BOT으로 만들지 않는다. 사용자 화면, 조회 API 어디에도 BOT으로 나오지 않는다. (보고서는 `agent_type`이 없는 경우를 말하지만, `SubagentStop`만 온 에이전트는 끝난 상태로만 보이게 되어 보여 줄 정보가 없으므로 `agent_type`과 무관하게 같은 규칙을 적용하는 것을 제안한다. 가정 A-1.)
- 숨김이 아니라 "만들지 않음"을 기본으로 한다. 숨기는 방식은 저장 데이터에 계속 쌓여 정리 규칙이 또 필요하다. 디버그를 위해 "무시한 내부 에이전트 수"를 보여 주는 것은 Could이며 이번에는 넣지 않는다.
- 진짜 BOT은 영향이 없다: `SubagentStart`가 오거나, `agent_id`가 든 도구 이벤트가 오면(S-06) 지금처럼 BOT이 생긴다.
- 끝난 BOT 정리: 상태가 완료(`done`)가 된 서브에이전트(BOT)는 유예 시간이 지나면 세션의 BOT 목록과 사무실에서 빠진다. 유예 시간은 L-2(기본 60초).
- 이벤트가 끊겨 종료(`ended`)로 판정된 BOT(작업 중·생각 중 10분 초과)도 목록·사무실에서 빠진다. 기존 10분 판정(D-6)은 바꾸지 않는다.
- 승인 대기 BOT은 어떤 경우에도 시간 때문에 빠지지 않는다(T1-2 "승인 대기는 종료로 보지 않는다" 유지).
- 책임자(`lead`)는 대상이 아니다. 세션이 살아 있는 동안 책임자는 그대로 보인다. 세션 자체의 표시·종료 규칙(D-6, D-17)은 바뀌지 않는다.
- 스킬 사용 기록과 BOT 호출 기록(T1-3)은 BOT이 화면에서 빠져도 지우지 않는다. 세션 상세의 스킬 횟수 집계가 줄어들지 않는다.
- 이미 저장된 가짜 BOT(예: 이번 확인에서 생긴 `a746…`, `ab67…`)도 화면에 나오지 않아야 한다. 처리 방식은 설계 확인 필요(Should).

### 수용 기준

- [ ] `SubagentStop(A1, agent_type=null)`만 보내면 그 세션의 에이전트 목록에 A1이 없고, 조회 API 응답에도 없다.
- [ ] `SubagentStop(A1, agent_type=qa)`만 보내도(`SubagentStart`·도구 이벤트 없음) 같은 결과다.
- [ ] `SubagentStop(A1)`만 두 번, 서로 다른 `agent_id` 두 개로 보내도 BOT이 늘어나지 않는다.
- [ ] `SubagentStart(A1)` → `SubagentStop(A1)`이면 A1이 생성되고 완료가 된다(S-05).
- [ ] `PreToolUse(A1)`이 먼저 오면 A1이 생성되고 작업 중이다(S-06 유지).
- [ ] A1이 완료된 시점부터 유예 시간 안에는 목록·사무실에 완료 상태로 보이고, 유예 시간이 지나면 둘 다에서 사라진다. 테스트는 시각을 바꿔 검증한다(실제로 기다리지 않는다).
- [ ] 작업 중 상태로 마지막 이벤트 후 10분이 넘은 BOT은 목록·사무실에서 사라진다. 9분 59초에는 보인다.
- [ ] 승인 대기 BOT은 24시간이 지나도 목록·사무실에서 사라지지 않는다("응답 없음" 표시만 붙는다).
- [ ] BOT(qa)이 `Skill` 도구를 쓰고 끝난 뒤 유예 시간이 지나도 세션 상세 스킬 횟수와 조회 API 스킬 집계가 그대로이고, `PreToolUse(Agent, qa)`의 BOT 호출 기록에 qa 1회가 남아 있다.
- [ ] 세션 종료(SessionEnd) 뒤에도 스킬·BOT 호출 기록이 남아 있다(T1-3 기존 기준 유지).
- [ ] 책임자는 모든 BOT이 빠진 뒤에도 목록·사무실에 남아 있다(세션이 종료로 판정되기 전까지).
- [ ] 한 세션에서 BOT 호출 없이 `SubagentStop`만 20번 와도(서로 다른 id) 사무실의 캐릭터 수는 책임자 1명이다(이번 확인 상황 재현).
- [ ] 같은 이벤트를 두 번 받아도 상태가 달라지지 않는다(T1-2 기존 기준 유지).

| HANDOFF "데이터 수집" | "1단계에서 `usage`와 `subagent.usage`는 저장하지 않는다(사용자 결정 2026-11-11)" |
| profile.md 기타 규칙 | "payload의 `usage`(토큰)는 받되 저장하지 않는다" |
| 범위 변경(2026-11-11) / 2026-11-12 결정 | "세션 model은 세션 상세 '모델' 표시용 유지" (그러나 값의 출처가 `SessionStart`뿐이라 놓치면 null) |

결정 취지는 "토큰 수와 비용을 다루지 않는다"이지 "모델 이름을 버린다"가 아니다. 모델 이름은 토큰도 비용도 프롬프트·응답도 아니다. 그래서 규칙을 좁혀 "토큰 수는 저장하지 않는다, 모델 이름만 예외"로 바꾸는 것을 제안한다(사용자 승인 필요, L-4).

### 문구 제안 (HANDOFF·profile 수정은 승인 후 책임자·scribe가)

- T1-1 요구사항: "`usage`와 `subagent.usage` 안의 **토큰 수**(`input`, `output`, `cache_creation`, `cache_read`, `messages`)는 받되 저장하지 않는다. 단 `usage.model`(모델 이름 문자열 하나)은 세션·BOT의 현재 모델 표시용으로 저장한다. `usage`의 형식이 틀리거나 `model`이 문자열이 아니면 모델만 무시하고 요청은 거부하지 않는다."
- D-21: "토큰 수 부분은 검사하지 않고 버린다. `model`은 문자열이고 길이 제한(D-2) 안일 때만 쓴다. 어느 경우도 400을 내지 않는다."
- T1-1 수용 기준 추가: "`usage.model`이 든 payload를 보내면 조회 결과의 해당 세션·BOT 모델에 그 이름이 있고, 토큰 수는 어디에도 없다."
- profile.md 기타 규칙: "payload의 `usage`의 토큰 수는 받되 저장하지 않는다. 모델 이름(`usage.model`)만 저장한다."
- 어떤 필드로 모델을 받을지(`usage.model` 재사용 vs 이벤트에 `model` 필드 별도)는 설계 확인 필요. 기획 요구는 "모델 이름만 저장되고 토큰 수는 저장되지 않는다"이다.

### 요구사항

- 세션 모델은 책임자(`lead`)가 쓰는 모델이다. 서브에이전트의 모델이 세션 모델을 바꾸지 않는다(가정 A-2).
- `SessionStart`를 놓친 세션(수집 설정 전에 시작한 세션)도 이후 이벤트에 모델 이름이 있으면 알아낸다.
- 세션 도중 `/model`로 바꾸면 다음 이벤트부터 새 모델이 된다.
- BOT(서브에이전트)마다 자기 모델을 가진다. 세션 상세 BOT 목록에 표시한다(Should).
- 모델이 한 번도 오지 않으면 지금처럼 표시하지 않거나 "알 수 없음".
- 모델 이름은 받은 문자열 그대로 보여 준다(예: `claude-haiku-5-5`). 보기 좋은 이름으로 바꾸는 것은 이번 범위가 아니다(Could).

### 수용 기준

- [ ] `SessionStart` 없이 시작한 세션에 `usage.model="claude-opus-X"`가 든 이벤트(예: `PostToolUse`)를 보내면 세션 상세 "모델"과 조회 API 세션 `model`에 `claude-opus-X`가 나온다.
- [ ] 같은 세션에 `usage.model="claude-sonnet-Y"`가 든 이후 이벤트를 보내면 세션 모델이 `claude-sonnet-Y`로 바뀐다(`/model` 변경 재현).
- [ ] `ts`가 더 오래된 이벤트가 늦게 도착해도 더 최근 이벤트의 모델을 덮어쓰지 않는다.
- [ ] `SessionStart`의 `model`이 있는 세션도 이후 `usage.model`이 다르면 최신 값을 따른다.
- [ ] A1(qa)의 이벤트에 `usage.model="claude-haiku-Z"`를 보내면 A1의 모델이 `claude-haiku-Z`이고, 책임자 모델은 그대로다. 반대로 책임자 이벤트가 A1의 모델을 바꾸지 않는다.
- [ ] 모델이 없는 이벤트(`usage` 없음, `usage.model` 없음)는 기존에 알던 모델을 지우지 않는다.
- [ ] `usage.model`이 숫자·객체·256자 초과 문자열이거나 `usage` 자체가 형식에 맞지 않아도 2xx가 오고 모델은 바뀌지 않는다(400 없음).
- [ ] `usage`가 든 payload(HANDOFF 예시 그대로)를 보낸 뒤 저장된 데이터·조회 결과·화면 어디에도 `input`, `output`, `cache_creation`, `cache_read`, `messages` 값이 없다(T1-1 기존 기준 유지, model만 예외).
- [ ] 모델 이름은 화면에서 문자열로만 표시된다(HTML로 해석되지 않는다).
- [ ] 한 번도 모델이 오지 않은 세션은 "알 수 없음"(또는 표시 없음)이고 오류가 없다.
- [ ] 실제 Claude Code 세션에서 `/model`을 바꾼 뒤 다음 응답이 끝나면 화면 모델이 바뀐다 `[사용자 확인]`.

### 먼저 확인

- 실제 이벤트에서 `usage.model`이 `SessionStart` 직후, `agent_id`가 있는 서브에이전트 이벤트, `/model` 변경 직후 이벤트에 어떻게 들어오는지(observe.mjs가 transcript 마지막 응답에서 읽으므로 첫 응답 전에는 없을 수 있다, 가정 A-3).

## 5. Task LIVE-01·02. 플랜 사용량 전송 신뢰성과 `/usage` 지연

### 5.1 먼저 확인 (수용 기준이 아니라 진단 절차)

LIVE-02 원인은 보고서에서도 추정이다. 대응을 정하기 전에 다음을 확인한다.

1. `AGENT_OBSERVER_DEBUG=1`로 statusLine stdin의 `rate_limits`와 같은 시각 `/usage` 값을 비교한다. 작업 직후(방금 응답이 끝남)와 한가할 때(10분 이상 방치)를 나눠 각각 3회 이상.
2. 같은 시각 서버의 `GET /api/plan-usage` 값과 `receivedAt`을 기록한다.
3. 판정

### 5.2 LIVE-01 요구사항 (전송 실패 복구)

- 서버가 늦게 켜졌거나 잠깐 꺼져 있어서 전송이 실패해도, 서버가 돌아온 뒤 별도 조작(`plan-usage.json` 수동 삭제 등) 없이 값이 도착한다.
- 서버에 실제로 도착한 값은 같은 값이면 다시 보내지 않는다(2026-11-12 결정의 취지 유지).
- Claude Code 화면 출력을 막지 않고, 실패해도 오류 없이 끝난다(exit 0). 같은 PC에서 최대 1분 1회 제한(D-22)은 유지한다.
- 수정은 dev-team-kit 쪽이다. 이 저장소에는 설치한 사본이 있고 테스트가 있으므로 사본과 테스트를 맞춘다.

수용 기준 (선택지와 무관하게 성립)

- [ ] 서버를 끈 상태에서 사용률이 바뀐 stdin을 넣어 스크립트를 실행하고, 서버를 켠 뒤 같은 PC에서 다음 실행(값은 그대로) 때 서버에 그 값이 도착한다(조회 API로 확인). 파일 삭제 같은 수동 조작이 필요 없다.
- [ ] 서버가 401·500을 돌려줘도 같은 결과다(전송 실패는 연결 거부만이 아니다).

- [ ] 스크립트는 전송 성공·실패와 관계없이 상태 줄 출력이 전송을 기다리지 않고 나오며 exit 0이다(T1-8 기존 기준 유지).

- [ ] 위 정보 중 승인 대기, 상태, 모델은 마우스를 올리거나(hover) 눌러야만 보이는 곳에만 있지 않다. 휴대폰에는 hover가 없으므로 상시 보이거나 터치로 열 수 있어야 하며, 승인 대기는 반드시 상시 보인다.
- [ ] 승인 대기 BOT이 있으면 사무실에서 문구("승인 대기")와 기다린 시간으로 보인다. 색만으로 구분하지 않는다. 24시간 넘으면 "응답 없음"이 보인다.
- [ ] 사무실에서 플랜 사용량(5시간·주간 사용률, 상태, 마지막 측정 시각)이 보이고, 값·상태는 조회 API와 같다(정상·한도 가까움·한도 도달·초기화됨·없음 모두). 프로젝트 필터와 무관하다.
- [ ] 사무실의 각 정보 값은 조회 API 값과 같고, 이벤트를 보낸 뒤 3초 + 1초 안에 바뀐다(T1-5 기존 기준 유지).
- [ ] 사무실에 동시에 보이는 BOT이 최대 10개(가정 A-4)여도 이름·상태 라벨이 서로 겹치거나 잘리지 않는다(Playwright 요소 위치 비교).
- [ ] 활동하지 않는 BOT은 사무실에 없다(LIVE-04 기준이 사무실에서도 성립).
- [ ] 세션이 하나도 없으면 빈 상태 안내가 나온다(기존 기준 유지).
- [ ] 기존 기능이 없어지지 않는다: 프로젝트 필터, 세션 선택, 정리·숨긴 세션 보기·다시 표시, 스킬 횟수 확인은 화면 어딘가에서 계속 가능하다(위치는 결정 후).
- [ ] 너비 390px와 1280px에서 가로 스크롤이 없다(기존 기준 유지).
- [ ] 토큰 수·비용·프롬프트·응답·도구 입력은 어디에도 나오지 않는다(기존 기준 유지).
- [ ] 조회 API 응답에 인증 토큰·비밀번호·쿠키 비밀값이 없다(기존 기준 유지).

### 접근성 요구

현재 사무실(`src/ui/Office.tsx`)과 벽 계기판(`PlanUsage.tsx`의 mini)은 `aria-hidden`이다. 정보가 세션 상세·상단 영역에 따로 있어서 중복을 피하려던 것이다. 사무실이 메인이 되면 이 전제가 사라지므로 다음을 요구한다.

- [ ] 사무실을 시각 없이도 이해할 수 있는 대체 수단이 있다. 스크린 리더의 접근성 트리에서 사무실의 BOT마다 항목 하나(역할 이름, 상태, 현재 도구, 모델, 승인 대기·기다린 시간)가 읽힌다. 항목 수는 화면에 보이는 BOT 수와 같다(Playwright 접근성 스냅숏으로 확인).
- [ ] 사무실의 정보를 키보드만으로 모두 얻을 수 있다(Tab·방향키로 BOT을 이동하며 읽거나, 같은 정보를 담은 목록·표로 이동). 포커스가 보인다.
- [ ] 같은 정보가 사무실 그림과 대체 수단에 두 번 읽히지 않는다(그림은 `aria-hidden`을 유지하고 대체 수단을 따로 두거나, 그림 요소에 이름을 붙이고 대체 수단을 숨기는 방식 중 하나. 방식은 디자인·설계 몫).
- [ ] 승인 대기가 새로 생기면 스크린 리더 사용자에게 알려진다(`aria-live` 등, 과도하게 반복하지 않는다) (Should). 실제 스크린 리더 확인은 `[사용자 확인]`.
- [ ] 색만으로 상태를 구분하지 않는다. 사무실의 글자·아이콘 대비는 DESIGN.md 기준을 따른다. 움직임이 있다면 `prefers-reduced-motion`을 따른다.

## 7. 비기능 요구사항

- 성능: 폴링 3초와 "이벤트 후 3초+1초 안에 화면 반영"을 유지한다. 유예·종료 판정 때문에 조회가 눈에 띄게 느려지지 않는다(세션·BOT이 많아도 기존 수준). 수치 기준은 설계에서 정한다.
- 보안: 모델 이름 외에 `usage`의 어떤 값도 저장하지 않는다. 모델 문자열은 길이 제한(D-2)을 적용하고 화면에서 문자열로만 출력한다. 토큰 값·인증 정보는 로그·응답에 나오지 않는다. 프롬프트·응답·도구 입력은 계속 저장하지 않는다.
- 호환성: `model`이 없는 이전 형식 payload, `usage`가 없는 payload도 오류 없이 처리한다. 설치된 observe.mjs·statusline.mjs 버전이 달라도 수집이 끊기지 않는다(D-21 취지).
- 접근성: 6절 "접근성 요구". 상태는 색만으로 구분하지 않는다.
- 테스트 가능성: 유예·종료 판정은 시각을 주입해 검증한다. 화면 확인은 실제 서버에 이벤트를 보내 만든다(가짜 응답 금지, 2026-11-12 결정 유지).
- 데이터 정합: 화면에서 빠진 BOT 때문에 스킬·호출 기록이 줄거나 틀어지지 않는다.

## 8. 가정과 미결 사항

가정
- A-1: `SubagentStop`만 온 에이전트는 `agent_type` 유무와 관계없이 BOT으로 만들지 않는다(보고서는 `agent_type` 없음만 명시). 진짜 BOT은 `SubagentStart`나 도구 이벤트가 먼저 오므로 영향이 없다고 본다.
- A-2: 세션 모델 = 책임자의 모델.
- A-3: `usage.model`은 에이전트별로 오고, 첫 응답 전에는 없을 수 있다. 실제 이벤트로 확인한다.
- A-4: 사무실에 동시에 보일 BOT 수는 최대 10개(역할 9개 + 같은 역할 중복 약간)로 본다.
- A-5: 내부 에이전트는 `SubagentStop`만 보낸다(이번 확인 결과). 내부 에이전트가 도구 이벤트도 보내면 BOT이 다시 생기므로 다음 실제 연결 확인에서 본다.
- A-6: 끝난 BOT 정리는 화면·조회에서 빼는 것이다. 저장 데이터에서 지울지는 설계가 정한다.

미결 사항 (L-목록은 9절)
- 이번 확인은 브라우저로 화면을 보지 않았다. 수정 후 실제 화면 확인이 필요하다 `[사용자 확인]`.
- LIVE-02 지연 크기 미측정.
- 기존 `.data`에 쌓인 가짜 BOT 처리.

## 10. 설계 확인 필요 (architect)

1. LIVE-04: `SubagentStop`만 온 id를 무시할 때, 이후 같은 id의 도구 이벤트가 오면 어떻게 하는가(생성하는 쪽이 기획 의도). 무시한 id를 기억할 필요가 있는가.
2. LIVE-04: 유예 후 제외를 조회 시점 계산으로 할지 저장에서 지울지. 스킬·BOT 호출 기록이 에이전트(BOT)와 연결돼 있다면 BOT을 지워도 기록과 집계가 남는지.
3. LIVE-04: 이미 저장된 가짜 BOT(`.data`)의 처리. 저장 형식 버전 변경(백업 후 새로 시작)이 필요한지, 화면 쪽 규칙으로 가릴 수 있는지.
4. LIVE-04: 내부 에이전트가 도구 이벤트도 보내는지 실제 이벤트로 확인(A-5).
5. LIVE-03: 모델을 `usage.model` 재사용으로 받을지, `model` 필드를 따로 둘지(후자는 observe.mjs 변경). 스키마가 `usage` 전체를 버리는 현재 방식(R-5, D-21)과의 양립. 세션 모델(`SessionStart`의 `model` vs 이후 값)과 BOT 모델의 갱신 규칙, 오래된 `ts` 이벤트의 처리.
6. LIVE-01: 전송 성공 확인과 "출력을 막지 않음"을 함께 만족하는 구조, 여러 세션 동시 실행 시 기록 경합. L-5(C)를 택하면 서버 "마지막 측정 시각"(`receivedAt`)의 의미가 바뀌는 문제.
7. dev-team-kit와 이 저장소 사본의 수정·동기화 절차(SEC-04와 같은 파일).
8. LIVE-05: 접근성 대체 수단의 구조(사무실 그림과 정보가 두 번 읽히지 않게). 다중 세션(L-7 b)이면 조회 API 응답 크기와 폴링 비용.
9. T1-2 R14 유예·종료 판정 위치, `effectiveStatus`와 BOT 목록 제외 규칙의 관계.
