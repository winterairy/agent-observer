# 보안 재검토: 쿠키 서명 정규성 검사 (이슈 #12, fix/cookie-test-flaky)

## 발견 사항
없음 (Critical/High/Medium/Low 0건).

## 근거
1. 정상 쿠키 거절/우회: 정규식이 서명을 `[A-Za-z0-9_-]{43}`으로 고정하므로 `+ / =`과 패딩은 정규식에서 이미 거절된다. 생성 쪽 `toBase64Url`은 32바이트를 항상 43자(패딩 제거)로 만들고 verify는 같은 함수로 재인코딩하므로 정상 쿠키는 항상 일치한다(만료 시각·길이와 무관, 서명 부분만 비교). 디코드는 `atob`가 남는 2비트를 버리는 관대한 방식이라 변형이 통했던 것이며, 재인코딩 비교로 표현을 1:1로 만든다. `-`/`_` 치환은 양방향 대칭이다. 우회 경로 없음.
2. 타이밍: 비교 대상은 공격자가 낸 값과 그 값의 재인코딩이다. 비밀이 없으므로 노출되지 않는다. HMAC 검증은 `crypto.subtle.verify`(상수 시간)로 마지막에 그대로 남아 있다. 키 파생 전에 거절하므로 오히려 불필요한 키 연산이 줄 뿐이다.
3. 변경 범위 밖 불변: 쿠키 형식(`v1.<exp>.<sig>`), 만료 검사, 키 파생, 길이 제한은 diff에 없다. 검증 호출은 `verifySessionCookieValue` 하나뿐이고 `hasValidSession`(src/auth/session.ts)만 호출한다. proxy·route가 쓰는 경로가 같은 함수다(proxy 별도 구현 없음).
4. 테스트: 서명이 다른 쿠키 200개에 대해 마지막 글자의 같은 상위 비트 변형(최대 3개)이 모두 false임을 확인하고, 원본은 true임을 같이 단언한다. 변형이 원 서명의 동치 표현이므로 수정 전 코드에서는 true가 되어 실패한다(책임자가 확인). 이 보고서에서는 테스트를 다시 실행하지 않았다.
5. SEC-01~09: 변경 파일(cookie.ts 1줄 추가, 테스트)에서 되돌려진 항목 없음. 쿠키 속성(HttpOnly·SameSite·Secure)과 로그 비노출 코드는 diff에 없다.

## 참고 (조치 불필요)
위조 가능성 자체는 변경 전에도 HMAC 서명(256비트)을 알아야 했으므로, 비정규 변형은 동일 서명의 다른 표기였다(우회가 아니라 쿠키 값의 중복 표현, 예: 값 기반 차단 목록을 쓸 경우에만 문제). 현재 그런 목록은 없다.
